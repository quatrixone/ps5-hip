# G4 runtime architecture: bounded offline comparison

Recommendation: select a small native HIP compatibility runtime as the main G4 implementation, using the real ROCm 6.2.4 headers/compiler ABI and existing checked loader, memory and submission substrate. Keep the standalone launch harness as a diagnostic control. Do not start a second production CLR backend or HSA runtime now. This is a development decision, not HIP/GPU/framework qualification; G2/G3 and native teardown prerequisites remain open.

## What CLR would genuinely save and cost

All following paths refer to the exact CLR revision above; file hashes are recorded separately.

- API/header integration is reusable: HIP declarations, compiler registration conventions, error enums, and public CMake interfaces. `hipamd/src/CMakeLists.txt:325-347` defines exported `hip::host`/`hip::device` around `amdhip64`. Our SDK needs a truthful eventual package, not a dummy imported library. `ndrange.cpp` is the sole backend-neutral implementation unit proved to compile on PS5 here. It is too small to justify importing CLR by itself.
- Upstream registration implements static function/global bindings and deferred program loading (`hipamd/src/hip_platform.cpp:50-103`); unregister synchronizes before removal (`177-185`). The existing single-TU PS5 control proves genuine constructor/stub/atexit ABI consumption separately, not these CLR functions. Linux `hip_platform.o` has 107 undefined symbols; `hip_error.o` has 38, including `hip::init`, `hip::tls`, host-thread and once machinery. Counts describe these O0 objects, not a minimal linked closure.
- CLR can save real ordering semantics: `hip::Stream` derives from `amd::HostQueue` (`hip_stream.cpp:31-33`); stream callbacks retain a completion marker and enqueue a second barrier until the callback finishes (`548-591`). `platform/commandqueue.cpp:39-56,314` couples worker/direct-dispatch handling to `createVirtualDevice`. `platform/command.hpp:72-204` owns event status, callback, completion notification and profiling state. A PS5 port still has to fulfill them; forwarding every method to a blocking submit is not equivalent async behavior.
- Ordinary `hipMalloc` already calls `amd::SvmBuffer::malloc` and installs memory-object/device bookkeeping (`hip_memory.cpp:295-345`), even without managed-memory opt-in. H2D/D2H/D2D use Write/Read/CopyMemory commands (`415-478`). A backend must implement pointer-range lookup, SVM allocation semantics and visibility/lifetime, not merely return a direct-memory pointer. Existing ps5-hip NativeMemory and queue holds are useful underneath either architecture.
- The device boundary is substantial: `rocclr/device/device.hpp:1261-1317` requires kernel, copy, map/unmap, fill, marker, SVM, flush, pending-handler and fence behavior; captured work also has an explicit `dispatchAqlPacket` entry. `1711-1740,1809-1876` require virtual-device, program, memory/view/signal, SVM and virtual-memory objects. A PS5 implementation can reject unsupported paths honestly; the pure virtual inventory is not a demand to implement every feature on day one. It does show that a complete upstream backend is more than replacing HSA queue writes. `device.cpp:589-625` currently initializes HSA/PAL backends only. `platform/program.cpp:111-176,488-560` creates device programs and builds the per-device executable.
- Host porting is independent of backend work. `os.hpp:68-106` mixes non-Windows FileDesc with Linux-only return selection; `thread/semaphore.hpp:29-52` has the measured semaphore branch. `os_posix.cpp` uses dlopen/dlsym (179-184), Linux thread-stack/affinity and prctl (310-325), vfork/exec (513-587), sysinfo and `/proc/self/exe` (721-736), mmap/mprotect/shm. Their Linux object has genuine unresolved imports recorded in the log. Not every facility must be reachable in our subset; replacing one missing include does not establish OS semantics.
- CLR has destructible TLS stacks/vectors (`hip_internal.hpp:588-605`, definition `hip_context.cpp:32`) and initialization in even error-facing API paths (`hip_internal.hpp:99-153`). The prior native registration control actually failed to link `__cxa_thread_atexit_impl` for a destructible thread-local vector and deliberately remained serialized instead. This is a demonstrated SDK integration gap, not a proof that threaded PS5 HIP is impossible. CLR would need a sound TLS destructor implementation/port, as would a broad custom runtime.
- Default build wiring adds Threads/rt (`ROCclr.cmake:128-131`), COMGR (`ROCclrLC.cmake:21-33`), and HSA/OpenGL/optional NUMA when the current HSA backend is selected (`ROCclrHSA.cmake:21-38`). Replacing that backend can remove its HSA/OpenGL dependencies; it does not remove all common compiler/OS/thread dependencies automatically. No PAL/HSA native link was attempted.

## Client-based choice and reassessment threshold

The real Prism client remains `e8fd209c975c80aa7fb36a8423571ff3b1b7e955`. Its inspected HIP CMake requires HIP >= 6.1, hipBLAS and rocBLAS, links `hip::host`, `roc::rocblas`, `roc::hipblas`, and rejects `GGML_STATIC`. Graphs/VMM/RCCL off still leave streams, events, host callbacks, asynchronous and pitched transfers, and BLAS. Neither candidate architecture solves missing math libraries or unqualified shader instructions. In particular, the gfx1030 SDOT4 route is not hardware-qualified by this choice; do not spoof device properties to satisfy ggml.

A small native runtime is preferred for the first examples because the actual compiler ABI, owned bundle loader, bounded launch arguments, direct memory and uncertain-completion quarantine already exist, while no upstream CLR OS/device port exists. The compilation comparison establishes concrete porting work; it does not prove a CLR backend would be slower or impossible. Reuse pinned public headers and measured compiler ABI. Use upstream semantics as the specification and preserve notices if source is reused; do not import a large source closure merely to obtain small utility functions.

Reopen the decision **before** adding a general asynchronous scheduler, cross-stream event dependency graph, host callback worker, shared memory pool with deferred retirement, graph capture or VMM. Also reopen if the pinned ggml link inventory cannot be covered by the bounded public contract plus separately qualified math libraries. At that checkpoint, compare an authentic PS5-linked CLR OS/Device/Program/VirtualDevice vertical slice against the proposed custom machinery, with one copy-kernel-event-free workload, failure propagation, threading and shutdown. Do not maintain both as production runtimes meanwhile. An HSA shim supplies no demonstrated shortcut here and adds signal/queue/memory-model obligations; it is not selected.

## Immediate complete implementation unit

The owned allocation/copy/free boundary and a distinct full-header memory ABI
control are now implemented and validated offline; see
[native data ownership](NATIVE_DATA_REGISTRY.md). Registration and capture controls
remain unchanged. The next unit must connect these measured boundaries to actual
native launch ownership; separate successful controls do not prove that connection.

Build a distinct experimental **single-TU, one-device, serialized default-stream vector example runtime** over the current registration core. Retain the old no-dispatch registration control. Scope the next offline milestone to an actual ordinary HIP compiler host stub flowing through registration, allocation registry, argument snapshot, checked planner, retained submission resources, blocking D2H observation, free and genuine compiler unregister. Use the measured 6.2.4/LLVM18 full-header vector fixture (73 outputs, 2 groups of 64, four explicit args, 288-byte kernarg including runtime geometry). Do not confuse its 288-byte kernarg extent with private-call scratch metadata from unrelated experiments.

Implement real `hipMalloc`/`hipFree`, H2D/D2H `hipMemcpy`, `hipGetLastError`/error text and explicit synchronize for that control; route `hipLaunchKernel` from the genuine push/pop configuration ABI into the existing checked loader/planner/backend. Keep unsupported streams, shapes, dynamic LDS, scratch, globals and unknown argument types explicit errors. Metadata gives argument count/offset/size: copy each caller-provided argument value before the stub returns, generate hidden fields internally, and resolve device-pointer ranges through owned allocation records (including interior offsets, overflow and use-after-free rejection). Loader/driver initialization belongs outside constructors. Unregister/free must drain known work or retain uncertain backing; never clear poisoned ownership to make teardown appear successful.

The current submission API waits synchronously; this first control may honestly serialize and block, but must not be sold as async stream support or become the permanent wait-after-every-operation design prohibited by plan 3.3. Public production capability discovery stays unavailable until native initialization and hardware prerequisites are qualified. Full G4 still requires multithreaded error/configuration isolation, multiple modules and device globals, reduction, tiled matmul, HIPIFY and error/lifecycle cases.

Offline acceptance: actual compiled constructor and ordinary launch stub, exact captured packed arguments/hidden geometry, host allocation/copy bounds, changed argument storage after call, input/output guards, repeated allocate/launch/free, partial registration failure, allocation failure, returned/exceptional submission failures and timeout retaining all resources, stale handles and genuine destructor cleanup. Synthetic backend callbacks are routing/lifetime tests, not ISA emulation or GPU proof. PS5 object/link/import/RELRO checks then prove only native binary preparation. A later frozen hardware milestone must still prove real output and safe lifecycle, including the unresolved .40 release-evidence prerequisite.
